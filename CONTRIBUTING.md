# Contributing

Use Python 3.11+ and uv, or enter the checked-in Nix shell.

```sh
uv sync --frozen --extra dev
make check
make build
```

Use conventional commits (`fix:`, `feat:`, `docs:`, `chore:`). Keep API changes in `client.py` and MCP tool/resource presentation in `server.py`. Preserve tool names and resource URIs where possible. Add regression tests for behavior changes and verify request fields against the relevant Listmonk handlers. Do not retry write requests automatically.

Tests use mocked HTTP responses by default. To run the integration suite, point it at a **disposable** Listmonk instance with a dedicated database:

```sh
LISTMONK_TEST_URL=http://127.0.0.1:9000 \
LISTMONK_TEST_ADMIN_USER=test-admin \
LISTMONK_TEST_ADMIN_PASSWORD=test-password \
  uv run --frozen --extra dev pytest tests/test_live_listmonk.py
```

The suite creates an API user and test data, exercises writes and maintenance, then removes its API user. Do not point it at production. CI runs the suite against Listmonk v6.0.0 and v7.0.0-beta.2 with a local SMTP sink. Unit tests cover HTTP errors, retry behavior, configuration, SDK registration, and corrected request contracts.

## Documentation

Install [oddship/moat](https://github.com/oddship/moat), then run `make docs`. Markdown lives in `docs/`; `docs/config.toml` sets the GitHub Pages base path. Tool reference content is generated by `scripts/generate_tool_docs.py` using the registered public MCP schemas. Regenerate it when tools change:

```sh
uv run --frozen python scripts/generate_tool_docs.py
```

## Releases

1. Update `pyproject.toml`, `__version__`, the HTTP User-Agent, package pins in docs, and `CHANGELOG.md`.
2. Run `uv lock`, `make check`, `make build`, `make docs`, and the live integration suite.
3. Merge the changes and verify CI on the default branch.
4. Tag that commit (`git tag vX.Y.Z`) and push the tag.

The publish workflow verifies the tag matches package metadata, reruns checks, builds and checks wheel/sdist, and publishes through PyPI Trusted Publishing. Only after publication succeeds does it create the GitHub release. Do not replace an existing published version; fix forward with a new version.
